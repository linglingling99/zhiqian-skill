# 人机协作 Skill

帮助 AI 在动手前真正理解用户和任务，把判断、证据和决定落在可迁移的本地文件里，再在明确范围内执行并验收。目标是一次自然对话，而不是"走流程"。

## 这是什么 / 不是什么

- **是**：以真实任务为入口的协作方法；轻量、中文交互、按需读参考。
- **不是**：人格测评、心理诊断、40 问调查表、重型项目管理；不把一次交流推断成永久能力等级；不把用户同意当成事实正确，不把 AI 反对当成事实错误。

## 何时触发 / 何时不触发

**触发**：任务模糊、跨领域、涉及重要变更或高风险、返工成本高、需要跨会话接续、需要先对齐需求再执行。

**不触发**：简单问答、单文件小改动、快速查证。这些直接处理，不套流程。

## 六条核心原则

1. **Understand before execute** —— 先理解再执行。
2. **Evidence before claims** —— 声称完成/正确前，先有当次验证证据。
3. **Write important state to disk** —— 重要状态落盘，换会话、换 AI 后仍可接续。
4. **Search capabilities only after the gap is known** —— 先确定能力缺口，再决定是否需要 Model / Skill / Tool / Connector / 开源项目。
5. **User confirmation ≠ factual verification** —— 用户同意不代表事实已被核实。
6. **AI disagreement ≠ user wrong** —— AI 有异议不代表用户错了；指出风险要有依据和条件。

## 信息分层：区分，不混为一谈

| 类型 | 含义 | 处理方式 |
|------|------|----------|
| 用户偏好 | 用户喜欢怎么做（风格、习惯） | 尊重，不做真假判断 |
| 用户要求 | 用户明确提出的目标与约束 | 记录为需求 |
| 用户自述事实 | 用户声称的事实 | 记录；高风险或有争议时核查 |
| 已核对事实 | 已用证据验证的事实 | 作为依据 |
| AI 推断 | AI 的推测 | 必须标为"推断/待确认" |
| 待验证假设 | 需要验证的猜想 | 列出最小验证办法 |
| 已确认决策 | 用户确认过的决定 | 记决策 ID；可被新证据重新讨论，但不得无记录改写 |

## 轻量流程：按复杂度递增

### 步骤 0：先读本地，不重复提问

- 若用户指定了资料主目录，先读 `INDEX.md` 找到当前任务，有 `TASK.md` 先读，避免重复提问。
- 没有资料目录时直接进入对话澄清，不强制先建档。

### 步骤 1：判断复杂度（先说出来，让用户可纠正）

- **简单**：目标明确、一次性、范围清楚 → 走短路径，直接处理，不建完整档案。
- **复杂**：模糊 / 跨领域 / 高返工 / 需跨会话 / 涉及重要变更或高风险 → 走澄清流程。

### 步骤 2：澄清，但有结束条件

- 一轮优先处理 1–2 个关键问题；一次只问一个核心问题，多用选择题。
- 目标、范围、关键资料、主要限制、验收条件足够清楚即可推进；不无限访谈，不追问与当前步骤无关的远期细节。
- 每轮有新增事实或决定时，给一句"新增 / 保持 / 待确认"反馈，并增量记录；没有新决定时不机械复述全档案。

### 步骤 3：研究，按缺口

- 先确认能力缺口，再检索 Model / Skill / Tool / Connector / 开源项目 / 案例。
- 本地已有能力优先；当前模型与工具够用就不换。确有能力缺口时，再说明为什么需要换模型、增加连接器或引入外部能力。
- 同时明确需要的数据来源与权限范围：读什么、写什么、是否允许上传/发布。
- 搜索、推荐、安装是三个不同阶段，不得默认自动安装未知技能。

### 步骤 4：记录，增量落盘

- 重要决定写入 `TASK.md`，来源与证据写入 `RESEARCH.md`，动作与错误写入 `LOG.md`，确认过的协作偏好写入 `PROFILE.md`。
- 保留当前有效版本与历史变更。写入前先读当前版本，避免覆盖并发变化。

### 步骤 5：生产资料就绪后，再执行与验证

- 复杂任务进入执行前，快速确认：目标、范围、关键资料、已确认决定、能力/数据/权限、主要风险、验收标准是否足够支撑下一步；不是要求所有问题一次解决。
- 对高成本或高不确定假设，优先做最小 Demo / Spike 验证，再决定是否扩大生产。
- 明确范围后再调用实际存在的能力；记录真实产物路径与实际检查。
- 用当次证据验收，不用"看起来完成""应该没问题"代替证据。
- 失败如实说明；没有执行环境时交付清晰的执行资料，不冒充完成。

### 步骤 6：沉淀与反馈

- 对照最初假设与实际结果，指出哪些判断被证实、哪些被修正、下一次应怎样判断；帮助用户和 AI 同时更新对问题的理解。
- 把新的有效经验按需归纳回本地资料；跨任务通用经验进入用户批准的知识区，不复制无关内容。

## 何时需要确认

- 简单已明确的任务：少确认，短路径通过即可。
- 模糊、复杂、重要变更、高风险、付费、发布、上传、安装、修改重要数据：逐项确认后再做。
- 简单不等于无需确认：范围哪怕一句话也要先说清再动手，避免在未验证的假设上返工。

## 边界与安全

- 公共 Skill 只放方法、规则、模板；用户真实资料放在用户自己的目录，绝不混入公共包。
- 不采集与协作无关的证件、住址、收入、心理特征。
- 无网络时：可整理需求与已有资料；外部核验标"未完成"，不虚构项目、Star、官网。
- 不能写文件时：输出可由用户保存的 Markdown，不说"已保存"。
- 未具备自动恢复机制时，靠用户显式提交本地入口文件恢复；不宣称自动跨会话记忆。
- 文档里的规则不能替代宿主权限控制；安装/修改/付费/上传/发布等须有明确授权。
