# 执行与验收｜把决定接到结果

**输入**：当前 TASK、研究驱动决定、实际能力与授权。**输出**：当前交付物、验收证据、明确限制，以及状态更新。

## 先明确此次“完成”是什么

用户只要可交给开发的方案，就以需求/交互/数据/验收充分为完成形态，不声称产品已运行。用户要可运行产品就要实际执行验证；要部署才检查外部可访问。分阶段交付不能把延期项伪装成完成。

每个必要需求至少能找到“负责动作 → 对应产物 → 验收办法”。可逆的小步骤优先；先做一个真实样例，再扩大。插件只按能力缺口使用，不重复安装多个接管流程的 Skill。手工目录/复制/打包在工具许可内由 AI 处理。

## 异常是一次状态转换

同类型动作连续失败 2 次，在第 3 次前记录 ROOT_CAUSE_CHECK：观察到什么、可能原因、下一次改变哪个条件。不是强制所有错误都重试两次。权限拒绝、破坏性风险和污染应立即停在边界。

把失败与恢复成本记录为真实事件；没有计费/时间数据写未知，不能从文本长度估算 Token。只停止自己启动、能核对身份的进程；不按模糊名称批量终止别的工作。长驻预览服务如用户需要保留，记录归属、用途和停止方式，而不是全部杀掉。

## Evidence before claims

验证必须匹配用户成果：代码运行/测试、文档字段与事实核对、数据对账、图像/页面的实际渲染查看分别不同。静态代码检查不能宣称 UI 可用，桌面截图不能宣称真机兼容，方案可读不能宣称已部署。

证据 E/V-* 标 ACTIVE / SUPERSEDED / INVALID。产物改变后旧证据先撤销或重新核对版本。最终只用适配当前结果的证据支持声明。每条未验证结论明确限制；不要给“0个问题”杜撰确定性。

## 交付前的一个综合检查

不是额外跑十个流程，而是检查一条链：
`当前要求 → 当前决定/依据 → 当前产物 → 当前验证 → 已同步的下一步`。

只收尾本任务的临时资源；保留实际验收证据与事故记录。打包保留结构、排除密钥/依赖缓存、校验压缩前后文件，不递归包含自己生成的包。哈希列表不哈希自身。

如果前置条件缺失，交付当前真实可用部分并标 NEEDS_REVIEW / BLOCKED，而不是把失败写成成功。

## 可选的机械回执

多文件、核心变更或交接且能运行 Python 时，按 `assets/templates/receipt.json` 生成当前任务根内 `checks/receipt.json`，再执行安装目录中的：

```text
python <skill-dir>/scripts/check_workspace.py --root <task-root> --receipt checks/receipt.json --delivery
```

AI 自己填实际路径，不让用户抄模板。只读检查会核对：任务/修订绑定、文件哈希、路径、依赖、变更覆盖和验收证据。无 Python 用人工/模型逐项检查并注明未执行脚本，不假装获得机器结果。

回执字段说明：
- schema_version 固定 "0.3"；task_id 和 revision 与 TASK 的 TASK_ID / REVISION 完全一致。
- files：每个已声明文件的 id/path/role/status/sha256/reviewed_revision/depends_on。路径相对任务根，禁止绝对路径、..、反斜杠、符号链接。current 恰好一个；deliverable 是此次实际交付，不一定是代码。
- checks：id、requirement（如 R-001）、status、evidence（证据文件 ID）、applies_to（被检查交付物 ID）。证据的 depends_on 要包含其检查对象。
- changes：id、affected、reviewed 均用文件 ID，真实逐项复核后填写，不为过关编造。
- 不把回执自己放进 files；输出的机械报告也不回填进自身哈希。一个冻结检查期间所有者暂停写入。

退出 0 只说明**已声明对象的机械一致性**。检查器不验证未列出的文件、不验证人类指令是否落实、不证实来源真实性、不隔离宿主，也无法拦截模型绕过它；SHA 不能代替事实核查。与语义审查结果一起报告，不把这些等同真正两组 AI 测试。

## 交接输出

默认只需一个当前入口，清楚说明交付在哪里、验证了什么、未解决什么、下一步一个动作。经验有真实增量才写；不需要为了总结再复制完整 TASK。没有独立新 AI 实际接手，最多报告“接续材料已准备”，不能声称交接成功率。
