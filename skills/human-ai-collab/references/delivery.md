# 执行与证据验收（delivery）

来自 verification-before-completion 的取精去杂：保留"需求与证据对应、未验证不能称完成、重新验证"，去掉"只适用于某具体仓库的测试命令、没有环境也强行跑命令"。

## 铁律

**没有当次验证证据，不做完成/正确/通过类的声称。**

## 声称前的门（gate）

在声称任何状态前：

1. **识别**：什么命令/检查能证明这个声称？
2. **执行**：完整跑一遍（新鲜的、完整的）。
3. **读取**：看完整输出、退出码、失败数。
4. **验证**：输出是否真支持这个声称？
   - 不支持 → 按实际状态陈述，附证据；
   - 支持 → 陈述时附上证据。
5. **之后**：才做声称。

跳过任一步，等于没验证，不是"已经验证过了"。

## 常见声称与所需证据

| 声称 | 需要 | 不算数 |
|------|------|--------|
| 测试通过 | 本次测试输出：0 失败 | 上次跑过、"应该会过" |
| 构建成功 | 构建命令退出码 0 | 只跑过 lint、日志看着正常 |
| Bug 已修 | 复现原症状的检查通过 | 改了代码、假设修好了 |
| 需求已满足 | 逐条对照清单 | 只看测试通过 |
| 委托完成 | 实际差异/产物在 | 只信"成功了"的汇报 |

## 需求 → 行动 → 证据 → 结果

把"要做什么"和"怎么证明做了"一一对应。只生成漂亮文档不等于完成原任务；必须保留下一步可执行的入口。

## 关键模式

- **测试**：跑命令 → 看到 N/N 通过 → 才能说"全通过"。
- **回归（红-绿）**：写 → 跑（过）→ 撤销修复 → 跑（必须失败）→ 恢复 → 跑（过）。
- **需求验收**：重读方案 → 建清单 → 逐项核对 → 报告缺口或完成。

## 危险信号（遇到就停）

- 措辞出现"应该""大概""看起来"。
- 在验证前就表达满意（"完成了！""没问题了！"）。
- 准备提交/发布/收尾但还没验证。
- 相信子代理/脚本的"成功"汇报。
- 只做了部分验证。

## 没有环境怎么办

没有执行环境时，不做"已完成"的声称；交付清晰的执行资料（要跑什么、预期结果、成功标志），并明确标注"未在本环境验证"。不虚构能运行的命令，不把推测兼容记成已支持。
