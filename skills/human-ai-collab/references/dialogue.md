# 需求澄清与方案确认（dialogue）

来自 brainstorming 机制的取精去杂：保留"理解意图→关键追问→提出备选→范围确认→获批再执行"，去掉"每个任务都要求完整规划""固定开发术语""上游自己的技能路由与产品开发链"。

## 任务分级：先分类，说出来

在第一次提问前，先给任务分档并**说出口**，让用户有机会纠正：

| 档位 | 适用 | 流程 |
|------|------|------|
| 探查（spike） | "能不能做""可行吗"之类，只要一个答案 | 说明要试什么，点头后尽量低成本求证；产出是结论，不是要保留的成果 |
| 小改（bounded） | 范围清楚、改动点已存在、可快速确认 | 问少数关键问题，给出简短方案，获批即做；不写正式文档 |
| 复杂（architectural） | 新项目、新子系统、改动影响他人或跨领域 | 完整澄清→备选方案→分节确认→书面方案→获批 |

**取舍原则**：两档之间拿不准时，先按风险较高的一档处理；发现隐藏复杂度就停下说明、升档。若新证据明确表明任务比预期简单，可以向用户说明理由后降档。目标是匹配真实复杂度，不把流程本身当成果。

## 澄清问题：一次一个，问关键的

- 优先理解：目的、约束、成功标准。
- 一次只问一个核心问题；需要展开时拆成多个问题，一轮 1–2 个。
- 能用选择题就用选择题，开放题也行。
- 如果请求描述的是多个互相独立的子系统（"做个平台，含聊天、存储、计费、分析"），先指出需要拆解，再逐个进入流程，不要在一堆细节上浪费提问。

## 提出备选：给选择，带推荐

- 提出 2–3 个不同做法，各说清取舍。
- 对话式呈现，先讲你推荐的方案及理由。
- 对每个方案做 YAGNI 精简，砍掉不必要的功能。

## 确认：获批再动手

- 无论哪一档，动手前都要说明意图并得到用户同意。
- "太简单不需要确认"是最大的返工来源：简单只意味着方案短，不等于可以跳过确认。
- 呈交方案和开始执行不能是同一口气；先呈交，停下，等明确同意。

## 常见反模式（这是最容易踩的坑）

| 心里想的 | 现实 |
|----------|------|
| "太简单，不用确认" | 简单 = 方案短，不是方案免审 |
| "范围清楚，方案显然，先做着" | 门槛在"获批"，不在方案长短 |
| "我熟悉这类，所以是小改" | 小改衡量的是有没有现成改动点，不是熟不熟 |
| "探查做出来了，代码就留下用吧" | 探查产出是结论；要保留代码是另一个新任务，重新分级 |
| "上一件事批准了，这一件也批准了" | 每件事各自分级、各自确认 |

## 方案自检（写完方案后过一遍）

1. 占位符扫描：还有没有 TBD / TODO / 没写清的需求。
2. 内部一致性：各节有没有互相矛盾。
3. 范围检查：够不够聚焦，是否需要再拆。
4. 歧义检查：有没有哪句话能有两种理解，有就明确成一种。

有问题当场改，不必走一轮重新评审。

## 结束条件

目标、当前范围、关键资料、主要限制、下一步验收条件足够清楚，即可推进。缺的是与当前步骤无关的远期细节时，不无限访谈。
